01

The real problem, and why structure wins

LLMs fabricate citations. A single call has no mechanism to re-check itself — whatever it emits, it emits. The architecture exploits an asymmetry the model alone can't.

Naive — outsource it to Claude

"Research this and cite sources." One pass. Confident prose, plausible-looking citations — a measurable fraction of which the source doesn't actually support.

  • No independent check of any claim against its source
  • Can't recover — first draft is the only draft
  • Failure is invisible and unmeasured

Agentic — a loop you designed

Decompose → research in parallel → independently verify each claim against the real source → iterate against the evaluator until it passes. Then prove the lift with numbers.

  • An evaluator agent re-checks every claim against ground truth
  • Failed claims trigger another generation, with feedback
  • Every step is traced, costed, and scored
Why it provably wins — verification asymmetry: checking whether a source supports a claim is far cheaper and more reliable than generating a guaranteed-grounded claim in one shot. The single call can't do this by construction. That's structural, not a tuning trick.

Anatomy of a single agent

Every agent is the same five parts in a loop. If you can write this loop, you can build any agent on the list below.

Goalwhat "done" means + a stop condition
Modelthe brain — decides the next action
Toolstyped functions it can call to act/observe

Loopact → observe → repeat until done or budget hit 
// the whole thing, honestly
state = init(goal)
while not done(state) and budget_left():
    action = model(state, tools)   # decide
    result = run_tool(action)       # act
    state  = remember(state, result) # observe
return answer(state)

📦 First question, answered once: where does the eval data come from — and how much do I need?
How much

Start with 20–30 examples. That's enough for a real gap between configs (a 10–15 pt difference clears the noise) without losing a weekend to labeling. To trust an automated judge, add a ~30-item human gold set and confirm the judge agrees. Grow only if the numbers look noisy.

Where to get it

① Your own artifacts — emails, repos, calendar. ② Public datasets — HotpotQA (research), Chinook / Northwind (SQL), SWE-bench-lite (code). ③ Synthesize — inject bugs into clean code, generate synthetic calendars, draft candidates with a strong model then check them.

The trick

Every eval row is (input, a checkable signal). The signal is the whole game: a gold answer, a known file, a constraint, a source quote. If you can check it in code, you can measure it.

I started two sets for you → evals/research_eval.jsonl + evals/research_gold.jsonl (for the ★ seed) and evals/sql_eval.jsonl (for #5). Plus evals/README.md with the sizing rules above.
The punchline — chain three of these, add an evaluator agent and a generations loop, and you've left "agent" behind for orchestration. That's the jump from #9 to the project on the other tab.

What you're building

VERIFIED-LOOP — a research agent that produces cited reports and refuses to hallucinate. It decomposes a question, researches sub-questions in parallel, then verifies every claim against the real source text and iterates across generations until the report is faithful. The output is a report where every sentence traces to a quote the source actually contains.

Why this one — the part that matters
  • It proves "agentic > prompting" with a number. Anyone can call an LLM. The rare signal is designing a system that measurably beats the naive call — and proving it with an ablation. That number is your entire pitch.
  • The win is structural, not luck. Checking a claim against a source is cheaper and more reliable than generating a perfect one in a single shot. A lone call cannot self-check by construction. You're exploiting that asymmetry on purpose.
  • It teaches the whole canon at once. Planning · parallel tool use · an evaluator / verification gate · a generations loop. Five reusable patterns in one finishable project.

Deep dive · S3 — the verifier + generations loop (where everyone gets stuck)

Why S3 is the whole project: steps 1–2 (plan, search, summarize) are roughly what one Claude call with web search already does. S3 is the part a single call cannot do by construction — independently check its own claims and improve against that check. Build this and you've crossed from "API wiring" to "agentic system design."

The verifier — step by step
  1. Each finding already carries the source URL it came from. Re-fetch (or reuse the cached) source text for that claim.
  2. Make a separate Claude call whose only job is to judge: "Here's a claim, here's the source text — does the text support it? keep / flag / drop, and quote the supporting line."
    Why separate: a fresh call with one narrow job and the real text in front of it is far more reliable than the original writer re-grading its own work. Verification is easier than generation — that asymmetry is the entire edge.
  3. Drop every drop, keep every keep, fix the wording on flag.
    Why it's the product: the dropped claims are exactly the hallucinated citations that make LLM research untrustworthy. Removing them is the value.
The generations loop — step by step
  1. Synthesize a report from the kept claims.
  2. Score it: faithfulness = claims_kept / claims_surfaced.
  3. If below target and budget remains, research the gaps, re-verify, re-synthesize.
  4. Stop when the score plateaus or the budget is hit.
    Why a loop, not one pass: one pass gives you whatever the first draft happened to contain. Iterating against an evaluator lets the system climb toward a target you can measure — 0.61 → 0.84 → 0.94. That climbing number is your proof.
The trap to name in an interview (and you've won): if the evaluator is just another LLM with the same blind spots, iterating against it can game the metric without real improvement (reward hacking). That's exactly why the verifier is grounded in the actual source text, and why you validate it against a 30-row human gold set. Say this out loud and you sound like someone who has shipped evals — because you have.
The one-line mental model — sign up for two APIs (Claude + Tavily), write an async loop that plans → searches → verifies → iterates, and measure it with an ablation. No GPUs, no model hosting, no Modal.
